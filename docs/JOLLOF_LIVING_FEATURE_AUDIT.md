## Executive conclusion

**Jollof Living has a substantial, working database-backed foundation, but the supplied code is not ready to operate as a trustworthy paid accommodation marketplace.** Many screens work as presentations or record-entry tools while the service they promise—payment, escrow, availability control, host approval, delivery or verification—is incomplete or absent.

A browser checkout successfully created a reservation and showed confirmation, **without collecting a payment**. In separate isolated tests, a blocked date remained bookable, arbitrary gift credit reduced a stay to zero, an unpaid future stay could release the escrow label immediately, and a suspended account could log in. New/unreviewed listings can fail to display even after approval. These are launch blockers, not cosmetic issues.

The strongest implemented areas are ordinary email/password accounts, database catalogue/content reading, password changes, internal notification read-state, subscriber capture, manual owner templates and CSV record exports. The weakest are financial settlement, authoritative availability, account safety/verification, cross-client authorization and the many buttons that only show success messages.

The inventory deliberately distinguishes **recording an intention** from **performing a service**. For example, notification feed records work; SMS/push delivery does not. A template can be saved; automatic template sending does not exist. Similarly, “paid”, “verified”, “connected” and “sent” labels are not proof of their underlying operations.

**Scope caution:** this is an audit of the repository, not a claim about the current production deployment or any services operated manually outside it. Future-only/research roadmap ideas are not counted as broken. Prominent unavailable capabilities, such as app-store buttons and SSO, are listed as non-operational rather than treated as regressions. Explicitly offered or claimed-live services are assessed against their implementation.

## Method and verification coverage

- Reviewed page controllers, the shared JavaScript UI, PHP authentication/repository/pricing/mail helpers, web APIs, mobile APIs, the supplied SQL schema, configuration structure and installer/package contents.
- Parsed **79 PHP files with no syntax errors**; `node --check assets/js/site.js` passed. Syntax success does not establish functional completeness.
- Built a **separate isolated copy** using PHP 8.3.33 WebAssembly and a local SQLite translation of the supplied MySQL schema: **59 tables and 442 selectively imported public catalogue rows**, plus synthetic audit accounts/transactions. Production accounts, password hashes, bookings, private conversations and production configuration were not used.
- Executed **98 API/database assertions**: **74 passed, 24 failed expected behavior**.
- Executed **57 browser/guard/responsive assertions**: **31 passed, 26 failed expected behavior**. These are ad hoc audit checks, not an existing repository regression suite.
- Performed **83 distinct route/role render checks**: **80 passed, 3 failed**. They cover anonymous, guest, owner and admin states. Rendering a page is not evidence that its service works.
- Checked seven key layouts at **390px** and ran **five automated axe WCAG scans**. Contrast and control-label/name failures remain.
- Used harmless stored HTML markers to test output handling; did not access another real user's data or perform a production exploit.

**Safety and limits.** Mail was disabled; no real money, messages to external recipients, provider callbacks, smart locks or external model calls were used. Native MySQL, transactional races, production infrastructure, deliverability, provider integrations, full accessibility, load/scalability and additional browsers/devices remain unverified. A request that merely lacked an external service was not treated as proof the service is absent; for example, email is partial/unverified, whereas payments have no charging implementation to exercise.

**Harness-only adaptations.** The isolated copy needed a PHP-WASM glob compatibility adjustment and a SQLite `GREATEST` function. After an emulator socket-abort error, browser static assets were fulfilled from the same local files while PHP pages/APIs continued over HTTP. Interrupted checks and an overly narrow menu selector were rerun; those harness failures are excluded from the final results. None of these adaptations changed repository application code.

## Reproducible acceptance examples for the repair work

Use a fresh non-production database and synthetic accounts. These are descriptions of local audit checks, **not instructions to test the public site with real bookings or payments**.

1. **Payments and gift credit:** create an ordinary stay with no provider success event. It must remain unpaid/unconfirmed as appropriate. Arbitrary credit must be rejected; only a paid, valid card may redeem, atomically and once. Retrying a webhook or request must not double-charge or double-credit.
2. **Inventory and rates:** an owner blocks a future day and assigns a different nightly price/rule. Public search/calendar/quote and final booking must agree. A block must reject booking; the quoted total must use the override. Two concurrent MySQL booking attempts for one interval must not both succeed.
3. **Account controls:** suspend a synthetic user, then try fresh web/mobile login and an existing session/token. All must be denied. Enable admin MFA, then test ordinary login, admin login and mobile login; none may grant admin privileges without the required second factor.
4. **Booking authorization:** a guest cannot approve their own request or change another guest's stay. An owner can approve/decline only their own property's requests. Mobile must not publish an unreviewed listing or submit an unearned review.
5. **Listing lifecycle:** submit an Abuja Villa with strict policy and a real test image, preview it while pending, approve it, then open its public page before any reviews exist. All fields and the image must persist; the page must render without null-data errors. A refresh must preserve an explicitly saved draft.
6. **State refresh:** create a named wishlist, add a comparison and perform a permitted booking transition. Check both the database and visible page immediately, without reloading. Returned state and screen state must agree.
7. **Financial display:** compare the exact browser checkout total with the final server quote, invoice and provider amount for promo, gift, weekly/monthly, add-on and split cases. Preserve the agreed snapshot even after rates change.
8. **Support and safety:** a property's Message button must open a real property/host thread. User message text must remain text, not executable markup. No “sent”, “dialling”, “verified” or “connected” message may appear without the corresponding action succeeding.

## Recommended implementation order

### 1. Contain risk before adding features

- Rotate any real credentials exposed in repository history, move secrets out of tracked files and protect/remove public SQL/ZIP backups. Review history and deployed copies; deleting the current file alone is insufficient.
- Disable real-payment/escrow/verification/keyless/connected/safety claims that the current implementation cannot support.
- Repair suspension, centralized admin MFA, mobile authorization, gift validation and stored HTML handling.

### 2. Complete a minimum trustworthy booking marketplace

- Implement a provider-backed payment and refund lifecycle with verified events and idempotency.
- Unify live status, capacity, minimum stay, calendar blocks, dynamic prices, policy and inventory locking behind one server service.
- Implement owner request approval/decline, check-in/checkout rules and policy-based cancellations/modifications.
- Finish listing fields, image storage, saved drafts, safe empty-detail rendering and authenticated moderation preview.
- Fix response envelopes and test UI → API → database → updated UI, not just endpoint success.

### 3. Make reporting and communication honest

- Reconcile invoices, points, host balances, occupancy windows and charts against authoritative events.
- Wire CMS blocks and campaigns to their actual consumers.
- Test transactional email through a sandbox and add delivery queues/statuses; implement operator/support workflows.
- Remove fixed financial receipts, referral statistics and capability badges from real account screens.

### 4. Add optional platform services and production assurance

- Implement referrals, reward redemption, external channels, wallet passes, corporate billing, real verification, advanced AI and native apps only after the core lifecycle is reliable.
- Ship safe installation/migration material, deployment rewrites and secrets guidance; fix canonical/sitemap behavior.
- Add automated regression tests/CI, native-MySQL race tests, backup/restore verification, monitoring, accessibility and multi-browser/device coverage. No tracked regression suite or CI configuration was supplied.

## Important distinctions and remaining verification

- **Real working code exists.** This is not merely a static mockup: authentication, CRUD, some validation, ownership checks, notifications, reports and stored reservations work. Conversely, a successful database write is not a successful payment, external sync or supplier booking.
- **Email is not declared absent.** Mail code exists; it was disabled for safety. SMTP/host mail deliverability must be tested separately. AI model availability, third-party credentials, bank settlements, taxes/remittances, actual property inspections and operating-team response times were not verified.
- **Financial/compliance copy is not evidence.** The source displays PCI/NDPR/GDPR/FIRS, escrow, insurance and remittance assurances without demonstrating those operational or legal guarantees. Obtain the relevant independent technical/legal/financial verification.
- **Deployment is not production-tested.** Missing rewrite/deny files in this checkout do not prove a live server lacks equivalent external configuration. The local URL results and repository exposure risks are reported as such.
- **Database differences are bounded.** Logic defects corroborated in PHP/JavaScript are not attributed to SQLite or WASM. Native MySQL enums, lock behavior, isolation and concurrency remain to be tested before release.
- **Mobile scope is backend-only here.** The API can support a future application, but this checkout does not establish an installable Android/iOS client or prove offline/biometric/voice/push features.
- **No fixes were made to application code.** Only this report, its matrix and sanitized evidence were added to the repository. Audit tooling, temporary libraries, fixture databases, accounts and screenshots were kept outside the repository.
